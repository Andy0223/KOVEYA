# 客戶關心與自然語言操作｜產品計畫補充 v1.1

日期：2026-10-20。狀態：Proposed（已納入規劃，尚未實作或驗收）。來源：Founder 轉述一位網球教練的經驗與新增產品需求。原 v1.0 的 173 條需求保持基準；本補充新增 24 條提案，結構化來源為 [planning_extensions.json](planning_extensions.json)。P1／P2 是相對優先級，沒有承諾上線日期。

## 新的產品洞察

部分學生並非不想上課，而是未將預約列為當下優先事項；教練主動關心可能促成再次預約。這是一個質性線索，尚不能推論所有學生、預設個人動機，或宣稱提醒已提升留存。

既有流程「供給方分享連結 → 客戶自主預約」之外，新增「完成服務 → 該再次關心 → 教練聯絡 → 客戶自行選擇是否與何時預約 → 完成服務」。KOVEYA Business 的價值包含維繫服務關係。

自然語言／語音是跨工作台的操作入口。長期方向是涵蓋平台內已支援的操作；首版必須先限定能力，不以『任何事』承諾尚未開發的功能，也不讓一句話直接授予所有未來操作權限。

## 第一個可交付版本

**客戶關心 P1：** 待關心名單、清楚原因、略過／延後、可編輯文字範本與服務連結；教練確認後自己用既有 LINE／WhatsApp 等渠道聯絡。不先做跨平台私訊機器人。複製訊息不代表已寄出，外部實際送出由教練回報並標示來源。

範例草稿：「嗨，最近還想安排網球課嗎？如果你有空，可以從這個連結看看合適時間；想先休息也可以告訴我。」僅為待確認範本，本次沒有傳送給任何人。初期優先用規則與範本，沒有每則訊息必須呼叫生成式 AI 的設計。

**文字操作 P1：** 建立服務草稿、查時段、準備自己的預約／申請；先做可審閱的操作卡片，確認後才寫入。教練的「建立課程」需先釐清是服務商品、單次預約或團課；目前團課未完成時不可假裝建立成功。

**語音 P2：** 點擊說話 → 轉錄並校正 → 同一套文字操作卡片 → 確認 → 呼叫既有 API。先驗證繁中、英文及中英夾雜；沒有預先選定付費辨識／模型供應商，不承諾所有手機瀏覽器皆原生支援。

**自動化 P2：** 以有明確範圍的工作流逐步擴展。唯讀查詢可自動執行；寫入、發布、取消、改期與對外發送先由人確認。將來僅在有明確規則、適用客戶同意與可撤銷範圍時，自動發送關心；不把「啟用一條提醒規則」擴大成任意代操作授權。

## 關心規則的初始假設

以「距離上次完成服務 N 天且沒有下一次安排」為候選條件，N 優先依雙方約定的服務頻率；7／14 天可作訪談範例，不是全平台預設。沒有上課歷史或固定節奏時，由教練選擇是否追蹤。教練可查看來源、原因、上次聯絡及下次可關心日。

已有預約、待確認申請、待回覆改期、已休息／退訂、當期已聯絡或不具聯絡許可時排除。發送前重新讀取狀態，避免客戶剛預約仍被催約。回約後停止當輪關心；取消後也不立即重啟催約，依新節奏與偏好處理。

「尚未預約的回訪」、「已預約的課前提醒」與「方案到期／續購」是不同用途；不可混用送達／已讀／同意狀態。不得用其他教練的預約內容做關心理由，也不依健康、財務或其他敏感推測來分類學生。正式渠道啟用前另完成對應通知與資料政策設計。

## 自然語言範例與確認內容

| 說法 | 平台應做的事 |
|---|---|
| 「新增一堂 60 分鐘網球體驗課，台幣 1,500，在台北，先申請再確認」 | 建立服務草稿；詢問未明確的時區、地點、可預約時間、緩衝與取消政策。預覽列出價格 TWD 1,500 與 REQUEST，確認儲存後仍為草稿，發布另行確認。 |
| 「下週三晚上幫我約網球」 | 從目前登入需求方出發，釐清教練／服務與時段；將相對日期解析成完整日期並顯示 Asia/Taipei 等已確認時區。查空位後準備預約卡，不把晚上猜成固定時間。 |
| 「找兩週沒來的學生，提醒他們預約」 | 只查目前業務資料、套用排除與偏好，展示名單及草稿；先不發送。逐筆審閱，第一版由教練自行聯絡。 |
| 「把小明改到星期五」 | 先釐清是哪位客戶與哪筆預約、完整日期時間；若改期能力尚未上線，回到既有表單。支援後建立改期提案，仍需對方接受。 |

提醒裡的預約連結仍需正常登入；連結不能成為免驗證的帳號入口。通知或語音不能成為對方同意預約、價格或改期的證據。

## 技術設計方向（未實作）

輸入 → 文字／語音 adapter → 意圖與結構化參數 → 伺服器驗證／釐清 → 版本化操作草稿 → 人工確認 → 既有 API → 正確結果及操作連結。

使用列舉的能力與嚴格 schema；後端根據目前 Session／租戶重新授權，不信任模型產出的身分、權限或任意程式。客戶備註、服務描述及外部內容都視為資料，不能升級成平台操作指令。交易沿用現有防撞、政策快照、狀態機、冪等與 Outbox；工具逾時後先查結果，不因重說一句就新增第二筆預約。

草稿需記錄來源、目前角色、明確對象、完整時間與時區、欄位／政策版本、待釐清項目及確認到期時間。確認綁定使用者、草稿版本與操作摘要；內容、政策或資源改變時重新確認。原始音檔預設不留存；轉錄／草稿紀錄也須有保存與刪除流程，不能為訓練任意長期保存客戶資料。

語音／模型供應商在小樣本準確度、手機相容性、延遲、成本與資料處理方式比較後再選。維持免費優先、低成本其次；測試使用上限，不因新增計畫就開通付費服務。保留文字與原表單，辨識失敗不阻斷核心預約。

## 分階段驗證與停止條件

1. **真實教練試用與規則研究：** 先讓目前約兩位潛在供給方操作既有流程。請教練在自己可合法管理的客戶中標示需要關心／不適合聯絡的案例，詢問既有聯絡方式與實際頻率；以少量自願學生回饋檢查是否感到被打擾。沒有把導入訪談當作同意自動訊息。
2. **P1 關心工作台：** 先驗證教練是否使用候選清單、是否省下人工整理、是否能促成自願回約；若大量名單不正確或客戶不願聯絡，調整規則而非增加訊息量。
3. **P1 文字助手：** 建立含正確／缺漏／模糊／越權案例的基準，驗證重要欄位、確認、失敗復原及租戶隔離。另與原表單比較完成時間、修正率、成功率；沒有可靠提升就不強制換入口。
4. **P2 語音與受控自動化：** 依文字助手與關心流程證據開放；語音和自動發送各自驗收，不因其中一項完成就宣稱另一項可用。

關鍵案例：已有預約者不被催約；退訂／暫停在待送期間生效；同一事件重試不重複送；開啟 LINE 不記為已送達；甲教練看不到乙教練資料；15／50、週三／週四、要／不要等轉錄錯誤不自動執行；相對日期／同名學生會釐清；服務草稿不自動發布；改期仍等對方接受；最後空位競爭只有一筆有效預約；回應遺失先查結果；不支援的團課／付款不假成功。
